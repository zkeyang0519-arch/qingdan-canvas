# 轻岛安装与更新

轻岛的正式 Windows 应用与 Cloudflare 网页分别发布。Cloudflare 更新网页和 API；Windows 安装包包含桌面主进程、受限 preload 和同一次构建的网页资源。桌面资源保持正式站点的 HTTPS origin，使现有 Cookie、IndexedDB 和线上 API 继续使用同一身份。

## 首次安装

构建产物位于 `output/desktop-release/Qingdao-Setup-<version>-x64.exe`。安装在当前 Windows 用户的 `%LOCALAPPDATA%/Programs/Qingdao`，快捷方式名称为「轻岛」，不要求安装 Node.js 或下载源码。程序支持从快捷方式直接启动；已有本机服务的网页启动入口优先打开正式安装版本。

旧源码版第一次迁移前，应先在旧窗口完成本地保存并从托盘退出。原登录与待办缓存不应被安装器复制或删除；配置档案由桌面 profile resolver 在本机安全接续。旧版本未持久化的输入框文字必须先保存为待办或另行保留，安装器无法恢复已经退出的旧进程中的纯内存文本。迁移到本次版本之后，新输入会按账号与画布持久化，供后续重启与更新恢复。

当前阶段按未签名方式发布 Windows 安装包。Windows 可能提示未知发布者，部分设备安全策略会直接阻止安装；不能承诺所有电脑都能点击放行，也不要要求用户关闭 SmartScreen 或其他安全保护。是否签名不改变登录、待办与输入的保存机制。

安装版每次启动后约 30 秒自动检查更新，此后每 6 小时检查一次，也可手动点击“检查更新”。发现更高版本后后台下载，用户点击“重启更新”才会保存状态并安装；没有新版本时继续使用当前版本，不重复安装。已经在运行时再次点击启动入口只会显示原窗口，不会每次点击都立即重新检查。源码版不启用安装包自动更新，首次需要安装一次 EXE。

## 从网页点击轻岛

从 0.3.1 起，网页按钮是安装、版本检查和启动的统一入口，与直接打开桌面快捷方式的后台检查有所区别：

1. 网页通过固定 `qingdao://open` 协议唤起安装版，再优先连接其 `127.0.0.1:8791` 入口。协议不携带登录凭据、下载地址或命令。浏览器首次可能要求允许打开应用和访问本机。
2. 安装版不依赖开发服务。它验证网页的一次性交接授权，检查固定 GitHub 更新源；版本符合时直接打开当前账号和画布。若本机开发服务已运行，也可使用原 `8790` 入口，由本机启动器检查是否安装及版本。
3. 已有本机服务但没有安装轻岛时，启动器下载、验证安装包的大小与 SHA-512，安装后再打开。首次使用且本机服务和轻岛都没有时，网页提供官方发布页下载入口；用户须运行一次 Windows 安装包。页面在等待安装期间会自动探测，安装完成打开轻岛后继续连接。
4. 有更高版本时先完成下载和校验，再确认原窗口的登录、待办、未提交输入均已保存，退出旧版并安装。网页等待新的应用进程完成一次新的账号/画布交接，才显示“已打开”。安装器发现轻岛仍在运行会停止，不强制结束进程。
5. 当前版本比发布源更新时不降级。更新源暂不可达但已安装时，可打开本机现有版本并明确提示检查未完成；没有安装时会提示下载失败，不把它记为成功。

0.3.0 及更早版本缺少自动退出控制入口；首次升至 0.3.1 需从托盘正常退出一次。之后的版本支持由网页启动流程安全保存、退出、更新和启动。没有发布 GitHub Release 时，网页与客户端都不能从空更新源下载版本；Cloudflare 更新网页不会自动创建桌面 Release。

## 构建

```powershell
npm ci
npm run desktop:package
npm run desktop:inspect
```

`desktop:package` 先构建网页，然后在 `.tmp/desktop-package` 准备最小桌面运行目录，只允许 `desktop/*.cjs`、`shared/desktop-origins.cjs`、运行依赖和构建后的 `dist` 进入安装包。不包含 `.dev.vars`、Cloudflare 配置、开发数据库、用户档案、Runner 设备凭据、源码或 Git 数据。

`desktop/package.json` 与根目录的版本号必须一致；桌面运行依赖由自己的 `desktop/package-lock.json` 锁定。`npm run desktop:package -- --dir` 生成解包目录，适用于隔离测试。`--skip-web-build` 仅供刚完成网页构建后的本地重复打包。

## GitHub 自动构建与发布

工作流为 `.github/workflows/desktop-release.yml`：

1. `main` 的桌面或前端相关文件变化时，在 Windows runner 上构建安装包并上传 Actions artifact，不直接替用户安装。
2. 发布桌面版本时，同时提高根目录和 `desktop/package.json` 的版本号及锁文件版本，推送对应 `v<version>` 标签，例如 `v0.3.0`。
3. 标签必须来自 `main`，与包版本一致。发布前检查选定的签名模式及更新源可匿名访问，验证通过才创建 GitHub Release。
4. 更新源为 `zkeyang0519-arch/qingdan-canvas` 的公开 GitHub Releases。若源码仓库是私有库，应改用独立公开的发行仓库或 HTTPS 下载源；不能把个人 GitHub Token 打进客户端。

当前未签名发布不需要证书配置，Release 说明会明确标注未签名。将来启用代码签名时，在 GitHub 配置：

- `WIN_CSC_LINK` Secret：Windows 代码签名证书，格式遵循 electron-builder 配置。
- `WIN_CSC_KEY_PASSWORD` Secret：证书密码。
- `QINGDAO_PUBLISHER_NAME` Variable：证书中的发布者名，客户端据此验证下载更新。
- `QINGDAO_REQUIRE_SIGNING=true` Variable：要求发布必须签名；缺少配置即失败。

全部签名配置为空且未强制签名时，标签流水线可发布未签名版本。只配置部分签名信息会失败，不能自动退回未签名；完整配置签名时会强制签名并在发布前检查应用与安装器的 Windows 签名。云签名服务需另行接入其专用构建步骤。

安装包、同名 `.blockmap` 和 `latest.yml` 必须作为同一版本发布。不要手工修改 `latest.yml` 的校验值。固定旧版安装包应保留为修复入口；自动回退需要先验证用户数据格式向后兼容，不能仅替换可执行文件便宣称回退安全。

## 更新验收

- 在隔离档案登录测试账号，打开画布，留下未提交输入；更新后确认账号、画布、待办、输入、停靠位置保持。
- 再测离线且有待同步修改、输入存储失败、下载中断、包校验失败和重复点击更新。
- 自动更新的端到端验收需要至少两个递增版本的安装包以及真实可访问的更新源；未签名方式也要实测 Windows 是否允许安装。启用签名后还须验证发布者身份。只有本地构建与单元测试通过时，不能记为公开更新链路已验收。
- 验收不得使用用户正在使用的档案做故障注入，也不得停止 Agent/Runner 的活动任务。
