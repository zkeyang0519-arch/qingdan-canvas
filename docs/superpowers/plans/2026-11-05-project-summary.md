# 第七步：项目总结与聊天上下文

沿用用户已确认的十步方案。本步提供第7页签、首次项目总结、显式刷新、新聊天总结与摘要进入轻单聊天，不提前做第8步自动队列或第9步正式工作区。

## 实现决定

- 总结复用现有 Codex `kind=summary` 运行、新会话和只读策略。复用 RunnerHub 的持久化存储、运行队列、租约及对账；摘要协调逻辑独立放在 project-summary 模块，避免增加一个会与现有执行状态重复的 DO。
- 首次选择已绑定项目以 initialize 创建总结；相同项目/聊天初始化与刷新页面不产生重复运行；显式新聊天、重新总结才创建新运行。
- 摘要包含现状、完成/进行/待办、阻碍、验证与不确定项；时间、目录、Git 基线和来源运行/会话来自执行端元数据。
- 最新总结失败时保留旧结果并标旧，只有用户明确选择使用上次摘要后才作为聊天背景。绑定授权变化不使用旧目录摘要。
- 摘要只读项目资料，不注入个人记忆或私人聊天；聊天继续遵守记忆遗忘与上下文长度限制。
- 真实联调发现通用命令读取进入审批等待；保留 read-only/on-request 策略，停止该测试运行后改用 Runner 原生、有数量/深度/字节边界的项目资料包。Codex只根据所附资料总结，未覆盖内容列入不确定项；资料包内容不能授予权限。此选择避免把扩大审批权限作为体验前提。
- 排队时的Git快照不能代表实际启动状态；只读总结在开始时重新采集原生 summaryContext，写任务继续严格验证原基线，原始执行快照不改写。
- 本地 Agent 启动器启用 PROJECT_SUMMARY_ENABLED；生产及预览默认关闭。密钥沿用第6步本机配置，不读取或输出其值。
- 在已有开发目录继续实现，保留前六步的未提交代码与真实验收数据；不新建会丢失这些依赖的干净工作树，不自动提交或部署。
