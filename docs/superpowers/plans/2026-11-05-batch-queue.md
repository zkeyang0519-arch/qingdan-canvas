# 第八步：批次自动推进、暂停与恢复

**Goal:** 一次提交的待办在同一 Codex 会话串行执行，验收和清单回写成功后才进入下一项；支持暂停、继续、立即停止和异常恢复，并以三个真实待办验收。

**Architecture:** 复用 RunnerHub 的持久化执行记录、命令/事件去重和租约，在其下增加纯队列状态与推进许可。Runner 在每项结束后做本机验收并等待服务端许可，同一批次保持一个 runId/threadId，各项使用各自 turnId。已有第5步是提交入口，第8步提供批次控制和验收结果。

**Tech Stack:** 现有 React、Workers/SQLite Durable Objects/D1、Node.js Runner、固定版本 Codex app-server；不升级依赖。

**Spec:** 用户本轮明确要求及原 [十步计划 Task 8](2026-11-03-qingdan-router.md)、[设计验收与推进部分](../specs/2026-11-03-qingdan-router-design.md)。同批次同会话优先于原设计的逐项新会话。

## 实现决定

- 在当前开发目录继续，保留前七步未提交实现、配置与验收数据；不提交或部署，不为隔离丢失当前依赖。
- 一个已授权不可变批次使用一个 runId/threadId，项与证据通过 taskId/index/turnId 标识。新提交才新会话。
- 新版批次用显式 managed 标记，旧运行按原协议读取；本机启用 BATCH_QUEUE_ENABLED，线上默认关闭。
- 普通暂停是做完当前项并完成验收/回写后暂停；立即停止走原取消命令，实际结束确认前不显示已停止。恢复不重新执行已通过项。
- 机器验收采用明确的 artifact 或本机预注册 command；自然语言完成标准仍为 human，不能因模型报告 done 就当人工通过。第5步提供文件存在/包含文字检查入口，保留原完成标准说明。
- 本步可执行的机器验收为文件检查。现有本机注册只有 checkId/label，没有固定可执行文件与参数授权，因此 command 返回需处理，不自动执行文本命令；超出支持范围的 JSON Schema 也不冒充通过。固定命令验收的进程树停止链需另行接入。
- 每次推进必须匹配当前命令和真实完成轮次、通过 required 验收、取得清单写回回执，并复核绑定权限和待派发项规格。写回临时失败只重试写回，不重复 Codex。
- 提交时固定本批次的顺序和任务集合。执行期间修改待执行项规格或顺序会阻断推进；用户停止原批次后按最新清单重新提交未完成项，不静默采用新条目或改写原授权。
- 只允许明确的机器验收失败自动修复一次，沿用原会话并重验全部条件；输入/审批、认证/配额、超时、网络和未知启动状态都停住，不自动猜测或重发。
- 复用现有 RunnerHub 存储与串行化，不增加与运行记录竞争的 DO。原设计的完整工作区改版留在第9步；本步交付可操作的第8步页签。

## 实现与验证

- [x] 后端队列：状态/revision、初始化、每项推进许可、暂停/恢复/人工验收、取消与异常、幂等恢复；测试 A→B→C、单活动项、旧结果/旧控制拒绝、回写失败不推进。
- [x] Runner：持久化项验收证据与当前身份、有限修复、等待许可后同会话续轮、终项完成许可；测试重复/失联/重启与暂停时不续轮。
- [x] 清单：可选结构化验收条件随规格持久化，新增/修改/聊天保存兼容，pending source复检；测试变化冲突及字段保留。
- [x] UI：第8步控制和历史，从第5步提交跳转，暂停/恢复/停止确认、人工验收和错误可见；测试请求幂等与项目隔离。
- [x] 真实三个待办：同thread不同turn，第一项后暂停且后项未启动，继续后顺序完成并更新清单；验证异常恢复和页面入口。
- [x] 全套测试、Worker/Runner类型、本地打包检查及一次独立审查。

## 审查重点

控制回执丢失后的幂等重试；暂停/取消与完成事件竞争；服务端尚未回写却开始下一项；协作者改规格或删除条目后的授权边界；原生轮次与模型验收文字混淆；重启后未知启动不得重新执行。
